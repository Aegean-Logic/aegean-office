# Graph delivers OneDrive files, not Office co-authoring

Yes, Aegean Office can have a OneDrive connection that feels like Office's for most of what users see. That means signing in once, browsing OneDrive in Open and Save As, saving straight to the cloud with the existing keep both / mine / theirs dialog, sharing from inside the app, and live co-editing between Aegean users. It cannot match the part that makes Office special: Word, Excel and PowerPoint co-author over a private Office-to-SharePoint channel that no third-party editor joins, so **Aegean users and Office users can never edit the same OneDrive file live together**. Everything achievable runs through Microsoft Graph, which is **free to call**, with a standard Entra app registration and **free publisher verification**. No Microsoft partnership or certification is needed. The hard limits are political rather than technical. Since mid-2025 ordinary users in work tenants can no longer consent to the `Files.ReadWrite.All` scope needed to open files *shared by colleagues*, so that feature needs an IT admin. The `recent` and `sharedWithMe` APIs that Office-style Backstage lists depend on **stop returning data after November 2026**. Browser editors served from customers' own Nextcloud hosts cannot sign in with one Aegean-owned registration. The recommended path is in stages: ship OneDrive sync-folder places first (about 3-5 weeks including a shared cloud-crate refactor, no Microsoft dependency), start publisher verification now, then build a Graph desktop backend for own-drive files and sharing (about 8-11 weeks). Defer OneDrive co-editing and browser editors until a customer pays for them, because both require Aegean Logic to run a hosted service.

## Office's OneDrive experience runs on a channel Aegean cannot join

The first thing to understand is why Office feels seamless, because it sets the ceiling. Office's Backstage is built on Microsoft cloud services, not on the sync folder. The Open tab shows "Recent files across devices" ([Microsoft Support](https://support.microsoft.com/en-us/office/collab-files/open-files-from-the-file-menu)). "Shared with Me" covers only OneDrive or SharePoint Online documents and needs a Microsoft 365 subscription ([Microsoft Support](https://support.microsoft.com/en-us/office/collab-files/excelexp/see-files-others-have-shared-with-you)). Personal OneDrive is added as a signed-in "place" ([Microsoft Support](https://support.microsoft.com/en-us/onedrive/upload-and-save-files-and-folders-to-onedrive)). When an Office file sits in a synced folder, the OneDrive sync app hands it over to Office. Office then saves only the changes ("differential sync") and merges co-authors' edits. This "Office file collaboration" setting has been **on by default for all tenants since May 2025**. Microsoft says plainly that without it, "when file conflicts occur, both versions of the file are kept" ([Microsoft Learn: Recommended sync app configuration](https://learn.microsoft.com/en-us/sharepoint/ideal-state-configuration)). A third-party app saving a .docx/.xlsx/.pptx in that folder gets exactly that fallback: a whole-file upload and a `Filename-COMPUTERNAME.docx` duplicate when versions collide ([Melbits KB](https://melbits.com.au/kb/why-does-onedrive-keep-duplicating-files)).

The wire protocol underneath is MS-FSSHTTP ("Cobalt"), with its binary MS-FSSHTTPB payload. It is publicly specified at revision 17.2 (February 2025), and the copyright terms allow implementations. However, Microsoft says it "has patents that might cover your implementations" and grants no patent licence by default ([MS-FSSHTTP, Microsoft Learn](https://learn.microsoft.com/en-us/openspecs/sharepoint_protocols/ms-fsshttp/05fa7efd-48ed-48d5-8d85-77995e17cc81)). All the third-party FSSHTTP work found is on the *server* side, letting Microsoft's editors co-author against non-Microsoft storage, such as the open-source WopiHost and its partial `UseCobalt` support ([WopiHost README](https://codeclimate.com/github/petrsvihlik/WopiHost/README.md/source)). No third-party *editor* was found that joins a live Office session as a peer. Doing so would mean emitting edits in Office's internal document model, which the specification does not describe. That is a reverse-engineering project with patent exposure, not an integration. Take it off the table.

Microsoft's official routes for third parties point the wrong way for Aegean. The Cloud Storage Partner Program is for vendors "whose business is cloud storage" who want to embed *Microsoft's* editors in *their* storage. Applicants must store files at rest on infrastructure they own or lease, and support editing in Word, Excel and PowerPoint for the web ([CSPP overview](https://learn.microsoft.com/en-us/microsoft-365/cloud-storage-partner-program/online/overview)). Its co-authoring extension, CSPP Plus, is also host-side ([WOPI extensions for coauthoring](https://learn.microsoft.com/en-us/microsoft-365/cloud-storage-partner-program/plus/coauthoring/coauthoring-protocol-about)). OneDrive and SharePoint Online have no setting to plug in a custom WOPI editor. Only on-premises SharePoint Server can be re-bound, which is how Collabora does it ([Collabora](https://www.collaboraonline.com/blog/how-to-wopi-binding-for-collabora-online-in-sharepoint-2016-server/)). The one supported hook into the OneDrive web UI is **File Handlers 2.0**. Contrary to the belief that they were retired, they were still documented as GA for OneDrive for Business and SharePoint Online in April 2026. They are "Not available" for personal OneDrive. They support "custom actions that launch into your app" for any extension, registered as an `addIns` manifest on the Entra app, with config changes taking 24-48 hours to appear ([Microsoft Learn: File handlers](https://learn.microsoft.com/en-us/onedrive/developer/file-handlers)).

The precedents tell the same story. No third-party suite was found that co-edits live with Office users on OneDrive. ONLYOFFICE DocSpace, the closest model, uses OneDrive as a backing store while its own server runs co-editing and writes the file back on close ([ONLYOFFICE DocSpace FAQ](https://helpcenter.onlyoffice.com/docspace/faq.aspx)). WPS Office edits through the sync folder ([WPS](https://www.wps.com/office-quick-solution/document-file-issues/connect-computer-or-phone-onedrive/)). LibreOffice merged a direct OneDrive connector and then never enabled it, citing Microsoft's terms of use ([LibreOffice Bugzilla 62437](https://bugs.libreoffice.org/show_bug.cgi?id=62437)). Distributions later declined to turn it on because they could not supply a client ID ([Arch FS#76293](https://bugs.archlinux.org/task/76293)). Aegean avoids the distribution problem because it ships its own signed binaries with its own registration. It still inherits the terms-of-use obligations covered below.

"Partial" means a weaker or account-limited version. "No" means it is not achievable by any supported means.

### The sync folder gets "Dropbox-like" OneDrive cheaply

On Windows the supported way to find OneDrive folders is the Cloud Files platform. `StorageProviderSyncRootManager.GetCurrentSyncRoots()` returns every registered sync root on Windows 10 1709 and later ([Microsoft Learn](https://learn.microsoft.com/en-us/uwp/api/windows.storage.provider.storageprovidersyncrootmanager.getcurrentsyncroots)). The documented registry layout uses "OneDrive" as its example provider ID and supports several accounts per user, "a work and a personal account" ([Microsoft Learn: Integrate a Cloud Storage Provider](https://learn.microsoft.com/en-us/windows/win32/shell/integrate-cloud-storage)). `CfGetSyncRootInfoByPath` tells whether a given file sits inside one ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/nf-cfapi-cfgetsyncrootinfobypath)). The friendlier `HKCU\Software\Microsoft\OneDrive\Accounts\Business1` keys and the `%OneDriveCommercial%` variables are undocumented and inconsistent between machines ([Multi Commander forum](https://forum.multicommander.com/forum/index.php/topic,3860.0/wap2.html)). The sync app also updates every 1-2 weeks, outside Office's update channel ([Microsoft Learn](https://learn.microsoft.com/en-us/sharepoint/sync-client-update-process)). Use the platform API as the source of truth and the registry only for labels.

Two behaviours matter more than discovery. First, **save atomically**. A community bug report describes OneDrive treating a delete-then-rename save as a user deletion, then propagating it and removing the new file ([claudeissues #65229](https://claudeissues.com/issue/65229-bug-edit-tool-silently-destroys-some-files-in-onedrive-synced-folders-via-non-de)). Write a temp file in the same folder and swap it in with `ReplaceFileW`, and never delete the original first. This is worth checking in the current save code even if nothing else in this report is built, because users already keep files in OneDrive folders. Second, **do not read online-only files in the background**. Opening a placeholder hydrates it transparently. But if that happens without "the user's specific instruction", Windows shows a toast that lets the user block the app from downloading files ([Microsoft Learn: Build a Cloud Sync Engine](https://learn.microsoft.com/en-us/windows/win32/cfapi/build-a-cloud-file-sync-engine)). Thumbnails and previews should check `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` first and show a cloud badge instead.

On macOS 12.1 and later, OneDrive lives in `~/Library/CloudStorage` on Apple's File Provider, and Files On-Demand "can't be turned off" ([Microsoft Support](https://support.microsoft.com/onedrive/fix-onedrive-files-on-demand-issues-on-macos-12-1-or-later)). Sandboxed processes have hit `EDEADLK` reading dataless files ([claudeissues #40783](https://claudeissues.com/issue/40783-bug-file-read-failure-on-macos-fileprovider-backed-paths-google-drive-icloud-etc)), so the apps should keep shipping as non-sandboxed Developer ID builds. Linux has no Microsoft client at all. Users run abraunegg/onedrive, rclone, or GNOME's GVfs backend, which has no sync or offline support ([OMG! Ubuntu](https://www.omgubuntu.co.uk/2024/04/set-up-onedrive-file-access-in-ubuntu)). On Linux the sync-folder route is therefore a user-configured folder, and Graph is the only route to a proper experience.

The sync-folder route needs no app registration and no tenant consent, and that matters a lot in enterprises. It is also the only route that works when an admin refuses to approve a third-party Graph app.

### Graph covers every file operation the Nextcloud backend already performs

The existing `Cloud` operations map one-to-one onto Graph v1.0. `files.list` becomes `children`. `files.open` becomes `/content` or the short-lived pre-authenticated `downloadUrl`. `files.saveAs` becomes a `PUT .../{parent}:/{name}:/content` with `conflictBehavior=fail`. Simple PUT uploads are now documented up to **250 MB** ([Upload small files](https://learn.microsoft.com/en-us/graph/api/driveitem-put-content?view=graph-rest-1.0)), which covers essentially every spreadsheet, document and deck. Upload sessions handle larger files in 320 KiB-multiple fragments, and they **return 412 Precondition Failed when `if-match` does not match the current eTag** ([createUploadSession](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0)). That is the hook for the existing conflict dialog. Compare `cTag`, the content-only tag, rather than `eTag`, so that a rename by someone else does not raise a false conflict ([driveItem resource](https://learn.microsoft.com/en-us/graph/api/resources/driveitem?view=graph-rest-1.0)). `delta` and a socket.io change channel can warn early that someone else has saved ([delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)). Throttling will not matter at interactive scale: users get 3,000 requests per five minutes, and apps get 1,250 resource units per minute per tenant. Microsoft asks ISVs to tag traffic as `ISV|AegeanLogic|GridLogic/x.y` and to honour `Retry-After` ([Avoid getting throttled](https://learn.microsoft.com/en-us/sharepoint/dev/general-development/how-to-avoid-getting-throttled-or-blocked-in-sharepoint-online)).

Do not use checkout as a soft lock. It "prevent[s] your changes from being visible until the document is checked in" ([driveItem: checkout](https://learn.microsoft.com/en-us/graph/api/driveitem-checkout?view=graph-rest-1.0)), which would confuse anyone co-authoring in Office. Optimistic concurrency with `If-Match` is the correct model, and it is the model the Nextcloud backend already uses.

### Sharing works, but personal and business accounts behave very differently

Graph v1.0 supports everything the current Share dialog does: `createLink`, `invite`, list, update and delete permissions, and `grant` to add people to an existing link ([Permission resource](https://learn.microsoft.com/en-us/graph/api/resources/permission?view=graph-rest-1.0)). All of it works with the user-consentable `Files.ReadWrite` scope ([createLink](https://learn.microsoft.com/en-us/graph/api/driveitem-createlink?view=graph-rest-1.0)). The account split is sharp. Personal OneDrive offers anonymous view, edit and embed links. Passwords and expiry need a Microsoft 365 Basic, Personal or Family subscription ([Microsoft Support](https://support.microsoft.com/office/3fcefa26-1371-401e-8c04-589de81ed5eb)), and `grant` is "Not supported" ([Grant permission](https://learn.microsoft.com/en-us/graph/api/permission-grant?view=graph-rest-1.0)). Business accounts add "People in your organization" and specific-people links, plus invites with expiry. "Can view without downloading" (`blocksDownload`) exists only in the beta API, which Microsoft says is not supported in production ([createLink beta](https://learn.microsoft.com/en-us/graph/api/driveitem-createlink?view=graph-rest-beta)). Passwords on business links are not documented in v1.0 at all. PATCH can change only `roles`, and not on organisation or people links ([Update permission](https://learn.microsoft.com/en-us/graph/api/permission-update?view=graph-rest-1.0)). Changing a link's audience or expiry therefore means deleting and recreating it, which gives a new URL. Tenant policy blocks surface without a documented error code. One Power Automate case reported "sharing disabled on the site" when the real cause was that anonymous links were blocked ([Dynamics community](https://community.dynamics.com/article/KA-24804)). The dialog needs to fall back from "Anyone" to organisation scope gracefully.

The people picker is now harder. `/me/people` works for both account types but is "in maintenance mode" ([List people](https://learn.microsoft.com/en-us/graph/api/user-list-people?view=graph-rest-1.0)). More importantly, `People.Read` joined the list of permissions that Microsoft's default consent policy blocks users from granting ([Microsoft Learn: Manage app consent policies](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/manage-app-consent-policies)). That round rolled out by July 2026 ([Topedia](https://blog.topedia.com/2026/05/microsoft-managed-default-app-consent-policy-will-block-8-additional-permissions/)). Typed email addresses should be the main path, with directory search as an admin-approved extra. Guests now follow Entra B2B rules: the SharePoint one-time passcode for external users was due to be fully retired by 31 August 2026 ([DW Results](https://dwresults.com/2026/04/08/external-file-sharing-microsoft-365-changes/)). The existing guest feature therefore maps onto `invite`, subject to each tenant's external collaboration settings.

## Consent, not code, decides who can use it

There is no Microsoft authentication library for Rust. Microsoft's desktop MSAL list stops at .NET, Java, macOS, Node and Python ([Microsoft Learn: Configure desktop apps](https://learn.microsoft.com/en-us/entra/identity-platform/scenario-desktop-app-registration)). The official `azure_identity` crate (v1.0.0) has no interactive or device-code user credential ([docs.rs](https://docs.rs/azure_identity/latest/azure_identity/)). The community `graph-rs-sdk` failed its docs.rs build ([docs.rs graph-oauth](https://docs.rs/graph-oauth)). The maintainable answer is to hand-write the OAuth flow, much as the Nextcloud Login Flow already is. Register one app as "Mobile and desktop applications" with audience `AzureADandPersonalMicrosoftAccount` and the `/common` authority. Use authorisation code + PKCE in the system browser against a loopback redirect, where **the port is ignored**, so ephemeral ports work. Microsoft prefers `http://127.0.0.1`, which has to be added through the manifest ([Redirect URI best practices](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url)). Offer device code as a fallback for locked-down machines ([Device authorization grant](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-device-code)). Refresh tokens last **90 days** and rotate on every use ([Refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)), so store them in the OS keychain. The Windows WAM broker is optional. Skipping it loses device-bound Token Protection ([MSAL.NET with WAM](https://learn.microsoft.com/en-us/entra/msal/dotnet/acquiring-tokens/desktop-mobile/wam)), so tenants that enforce it through Conditional Access may block a browser-flow app. That is an inference to test, not a documented block.

The consent picture shapes the product more than any API. Microsoft's managed consent policy is **the default for new tenants and updates itself**. It now stops ordinary users consenting to `Files.Read.All`, `Files.ReadWrite.All`, `Sites.Read.All` and `Sites.ReadWrite.All`, plus mail, calendar, contacts, tasks and `People.Read` ([Microsoft Learn: Manage app consent policies](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/manage-app-consent-policies)). The file and site block (MC1097272) reached all default tenants by August 2025 ([Office 365 for IT Pros](https://office365itpros.com/2025/06/19/app-consent-policy-user-app-consent/)). `Files.ReadWrite`, `User.Read` and `offline_access` remain user-consentable. Those three are enough for sign-in, browsing, open, save, AutoSave and sharing on the user's *own* OneDrive. Files that colleagues share from *their* drives are a different matter: Microsoft says shared items cannot be accessed "if the request doesn't contain one of the `*.All` permissions" ([drive: sharedWithMe](https://learn.microsoft.com/en-us/graph/api/drive-sharedwithme?view=graph-rest-1.0)). In a default work tenant, then, "open what a colleague shared with me" needs an admin, either through tenant-wide consent or the admin consent workflow ([Configure user consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-user-consent)). Design for incremental consent. Ask for `.All` only when the user first opens a shared item, and explain that IT may need to approve it. Personal Microsoft accounts sit outside tenant policy and can presumably grant `.All` themselves. That is an inference to confirm in testing.

**Publisher verification is free and effectively mandatory.** Unverified multi-tenant apps registered after November 2020 are blocked from user consent in tenants that use risk-based step-up consent, and they carry an "unverified publisher" warning ([Publisher verification overview](https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview)). The requirements are a verified Microsoft AI Cloud Partner Program Partner Global Account in Partner Center, the app registered with a work account in a tenant linked to it, a publisher domain that is not `*.onmicrosoft.com` (aegeanlogic.co.uk, DNS-verified), and an admin with MFA. "Microsoft doesn't charge developers for publisher verification" ([same source](https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview)). The existing Azure tenant used for Artifact Signing is the natural home, provided aegeanlogic.co.uk is verified as a custom domain there. The Partner Center paperwork is the long pole, so start it first.

The remaining obligations are legal rather than financial. Graph file APIs are unmetered. The only metered OneDrive call is `assignSensitivityLabel` at US$0.00185 per call ([Metered APIs](https://learn.microsoft.com/en-us/graph/metered-api-list)). The Microsoft APIs Terms of Use (October 2025) require minimum permissions, a privacy statement "as protective as the Microsoft Privacy Statement" with links that let users revoke consent, and deletion of data when users leave. They also prohibit using the APIs "to migrate Customers away from a Microsoft Offering" without customer approval. Microsoft "may change or discontinue" the APIs at any time, with liability capped at US$5 ([Microsoft APIs Terms of Use](https://learn.microsoft.com/en-us/legal/microsoft-apis/terms-of-use)). The migration clause is worth a lawyer's half-hour, because an office suite that also offers Nextcloud could be read as competing, even though editing a user's files in place is not migration. The client ID of a public client is not a secret, so publishing it in the open-source repos is normal practice. Forks should register their own IDs, because credentials are non-transferable. On branding, use plain-text "OneDrive" labels and a generic cloud icon: Microsoft logos need a licence and must not imply endorsement ([Microsoft Trademark and Brand Guidelines](https://microsoft.com/legal/intellectualproperty/trademarks)).

## Browser editors cannot sign in from customers' own servers

The WASM editors are where the Nextcloud model and Microsoft's model clash. Today each editor runs from the customer's own Nextcloud host, so every install has a different origin. An Entra app that signs in both personal and work accounts **cannot use wildcard redirect URIs**, is **capped at 100 redirect URIs** (a limit that "can't be raised for security reasons"), and cannot put query parameters in them ([Redirect URI best practices](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url)). One Aegean-owned registration therefore cannot serve arbitrary self-hosted origins. Browser registrations also suffer a **24-hour refresh-token cap** for the SPA platform ([Refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)), so browser users re-authenticate daily, unlike the 90-day desktop experience.

There are three ways out, and each changes the business model in a different way. In the first, **customers bring their own registration**: a self-hosting organisation registers its own Entra app for its own origin and pastes the client ID into the Nextcloud app's admin settings. That fits work tenants well, because their admin can grant `.All` consent at the same time, but it does nothing for personal accounts. In the second, **Aegean runs a central auth origin** that receives the code and hands off to the customer's host. Microsoft suggests a single redirect URI plus an integrity-protected `state` parameter for many-subdomain cases, and warns about open-redirect risk ([same source](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url)). This puts an Aegean-operated service in every customer's sign-in path. In the third, **OneDrive in the browser is offered only from an Aegean-hosted origin**, such as an `app.aegeanlogic.co.uk` that serves the same WASM editors. That is one redirect URI, and it is also the only kind of endpoint a File Handler can point to. Option three is the cleanest. Option one is a good add-on for enterprise self-hosters.

File bytes add a second browser problem. Graph's `/content` answers with a 302 redirect, which "is explicitly prohibited when a CORS preflight is required". Microsoft's documented workaround is to fetch the pre-authenticated `downloadUrl` without an Authorization header ([Download driveItem content](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0)). MC1492958 retires exactly those URLs from April 2027, and its notice does not mention CORS. A browser save and load path built today must be re-validated against the tenant opt-in controls before April. Microsoft's File Picker v8 can supply a native-looking OneDrive Open and "save-as" tray in the browser. But it documents `Files.Read.All`/`Sites.Read.All` scopes, which are now admin-gated, relies on SharePoint rather than Graph tokens for business accounts, and needs the host origin in its messaging setup ([File Picker overview](https://learn.microsoft.com/en-us/onedrive/developer/controls/file-pickers/?view=odsp-graph-online)). It is better to reuse Aegean's own egui Open dialog over Graph in the browser too, and to keep the picker as an option for admin-consented tenants.

## Live co-editing on OneDrive needs a relay Aegean hosts itself

The existing relay lives inside each app's Nextcloud server app and authorises users through Nextcloud. A OneDrive user has no Nextcloud identity, so OneDrive co-editing needs a relay that authorises through Graph instead. The workable design follows the ONLYOFFICE precedent ([ONLYOFFICE DocSpace FAQ](https://helpcenter.onlyoffice.com/docspace/faq.aspx)). Key sessions by `driveId/itemId`. Admit a client only after the relay calls `GET /drives/{d}/items/{i}` *with that user's own delegated token*; success proves access, and permissions show whether the user can write. Run the existing op sequencing, cursors and per-user undo unchanged, and write snapshots back with `If-Match`. Treat Office users and sync-client edits as external changes, detected through eTag mismatches, delta or change notifications, and show them as "changed outside Aegean, reload". That works for personal and business accounts and needs only the standard Entra registration. In return, Aegean Logic operates an internet-facing service that briefly holds users' tokens and document content. That makes it a data processor with uptime, security and UK GDPR obligations, which the self-hosted Nextcloud model avoids.

Microsoft's own building blocks do not help here. Azure Fluid Relay is a JavaScript-centric service. One partner page claims it retired in September 2025, while Microsoft's own overview, updated August 2026, shows no retirement notice ([innFactory](https://innfactory.de/en/cloud/azure/products/fluid-relay/); [Microsoft Learn](https://learn.microsoft.com/en-us/azure/azure-fluid-relay/overview/overview)). Either way it does not interoperate with Office co-authoring and would mean rewriting the Rust collaboration core. The cheapest hint of Office activity is Google's model of presence and "newer version saved" alerts rather than merging ([Google Drive Help](https://support.google.com/drive/answer/9406611)). Aegean can approximate it with change notifications.

## A staged plan that keeps each step useful on its own

The effort figures below are engineering estimates for one experienced Rust developer. They assume the existing `Cloud` interface and dialogs are reused, and they are not sourced from the research. The single largest saving comes first: today the three apps each carry their own ~1,600-line `nextcloud.rs`, so a OneDrive backend written three times would cost three times as much. Extracting a shared `cloud` crate first, with Nextcloud as its first implementation, roughly halves every later stage.

**Recommendation: build stages 0-3, start publisher verification this week, and hold stages 4-5 until a paying customer asks for OneDrive co-editing or browser access.** Stages 0-3 take about 11-16 weeks. They give Aegean Office the experience most people mean by "works with OneDrive like Office does": sign in once, OneDrive in Open and Save As, cloud saves that never silently overwrite, sharing from the app, and version history. They also keep Aegean's current architecture, in which Aegean Logic runs no servers and holds no customer data. Stage 1 alone is worth shipping first, because it costs little, depends on nothing from Microsoft, and keeps working in tenants whose admins refuse Graph consent. Stages 4 and 5 are a different business: they turn Aegean Logic into an operator of a multi-tenant cloud service. That decision should rest on demand, not on a wish for feature parity. Do not invest in MS-FSSHTTP, CSPP, Fluid, `checkout`, or the soon-dead `recent` and `sharedWithMe` endpoints. Market the result honestly as "open, save and share OneDrive files; co-edit with other Aegean users", never "co-author with Microsoft Office".

### Questions to settle by hands-on testing before committing to stage 2

A week of testing with one personal account, one premium personal account and two work tenants (one on default consent, one locked down) would remove most of the remaining uncertainty.

## Conclusion

The practical finding is that "like Office" splits into two very different problems. The *file* experience (where documents live, how they open and save, how they are shared) is an open, free, well-documented API surface. It fits Aegean's existing `Cloud` abstraction almost perfectly, and the keep both / mine / theirs dialog already matches Graph's concurrency model. The *collaboration* experience is either closed (co-authoring with Office) or forces Aegean to become a cloud operator (co-editing among its own users on OneDrive). The Nextcloud integration hides that difference because the customer's own server hosts the relay. With OneDrive there is no customer server to hide behind.

The forces at work also favour a narrow integration. Microsoft is steadily restricting broad scopes and retiring convenience endpoints, and every round so far has left the narrow, own-drive, per-item operations untouched. A OneDrive backend built on that narrow core, sitting alongside the sync-folder fallback that needs no consent at all, is likely to stay stable for years. Anything built on Shared with me, picker iframes or redirect tricks will need rework each time Microsoft tightens something.
